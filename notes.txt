Стандартное правило именования событий (Event) в Kafka -- СущностьДействиеEvent. Например: PaymentCreatedEvent

При этом Event - часть Message. Event сериализуется и является составной частью (телом, скорее всего) Message.
Message же при этом содержит Key - ключ, по которому производится распределение по партициям (если указан); Timestamp -
время создания сообщения; Headers - заголовки в формате ключ-значение для хранения дополнительной информации.

Топик делится на партиции, в которых сообщения упорядочены. Упорядочены они по времени добавления, и считываются
только в таком порядке. При этом для каждого потребителя хранится для каждой партиции оффсет -- смещение относительно
начала партиции, которое определяет следующее считываемое сообщение. При этом нельзя вставлять данные в середину или
начало партиции - только в конец, чтобы сохранялась упорядоченность. Хранимые данные еще и неизменяемы. Их нельзя
удалить и изменить вручную. Удалятся они только после того, как пройдет заданное количество времени. По умолчанию
это количество времени составляет семь дней.

Партиции - единицы параллелизации топика. Из них чтение идет параллельно, поэтому нельзя полагаться на порядок отправки
сообщений, если они записаны в разные топики. Чтобы сообщения обработались в определенном порядке, нужно указать
сообщению ключ. При указании одного и того же ключа сообщения будут попадать в один и тот же топик.

Кафка поддерживает репликацию. Можно создать кафка-кластер, где один сервер будет выступать в качестве лидера, а
остальные - в качестве фолловеров. Лидер будет производить запись сообщений, а фолловеры будут реплицировать у себя
записанные в лидера данные. При отказе лидера, им становится один из фолловеров. То есть лидер принимает данные от
продюсеров, отправляет данные консюмерам, а также отправляет данные на фолловеров для репликации.
Если бы такая схема работала на всю структуру и лидер для каждого топика и каждой партиции был бы один, он бы стал узким
горлышком, а остальные сервера в кластере бы простаивали. Чтобы избежать этого, используется механизм распределения
лидеров для каждой партиции каждого из топиков. Таким образом каждый из серверов кластера становится лидером для какого-
то подмножества партиций, и нагрузка распределяется между всеми (поровну, видимо).
Как уже и было сказано, при отказе лидера какой-то партиции, лидером автоматически назначается какой-то из фолловеров.



Первый запуск кафки.
После установки кафки находим папку со скриптами (bin) и переходим в нее
Затем выполняем команду для рандомного uuid: ./kafka-storage.sh random-uuid (или виндовс аналог)
Новые версии kafka работают только с kraft, zookeeper убрали, поэтому форматировать ничего не нужно
Для запуска в виде docker контейнера можно указывать свойства из .properties файла в виде переменных окружения, заменяя
"." на "_" и добавляя префикс "KAFKA_"
Сгенерированный id будем использовать как id кластера - переменную окружения CLUSTER_ID
После этого запускаем контейнер с этой переменной окружения и видим, что все
У нас запустится кластер с одним сервером

Для запуска нескольких серверов в кластере для каждого из них нужно немного поменять конфигурацию запуска, опять же
используя переменные окружения
Нужно установить следующие переменные окружения:
KAFKA_NODE_ID - id сервера в кластере в формате одного числа. Числа должны быть разными для разных серверов (1, 2, ...)

KAFKA_LISTENERS - хост и порт для контроллера и брокера в формате
PLAINTEXT://{имя_сервера_в_сети_docker}:9092,CONTROLLER://{имя_сервера_в_сети_docker}:9093. На этих адресах сервер будет
слушать внутри контейнера

KAFKA_CONTROLLER_QUORUM_VOTERS - контроллеры, которые в рамках кластера управляют распределением лидеров, фолловеров. В
формате {id_сервера_в_кластере}@{адрес_контроллера_с_хостом_и_портом} для всех серверов через запятую

KAFKA_ADVERTISED_LISTENERS - строка подключения к брокеру для внешних клиентов в формате
PLAINTEXT://{адрес_сервера}, где адрес можно выбрать либо внутренний, для доступа из Docker-сети, либо localhost:порт
для доступа с хостовой машины.

KAFKA_LOG_DIRS - директория с логами, метаданными и снапшотами. Всем можно указать /var/lib/kafka/data и создать
отдельный volume

KAFKA_PROCESS_ROLES - роли сервера в кластере (контроллер, брокер, или обе)

KAFKA_CONTROLLER_LISTENER_NAMES - имя слушателя, который является контроллером, из проперти KAFKA_LISTENERS
Мы указали двух слушаетелей: CONTROLLER и PLAINTEXT. И именно CONTROLLER должен быть контроллером, поэтому его имя и
нужно указать.




Kafka topic CLI

./kafka-topics.sh \

./kafka-topics.sh \
    --describe \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092

Можно проверить, что партиции обрабатываются в асинхронном формате, и при этом сообщения с одним и тем же ключом
попадают в одну и ту же партицию. Проверять будем на топике с несколькими партициями - payment-sent-events-topic
Для этого запишем 6 сообщений с ключом key и значениями A,B,C,D,E,F, а также 6 сообщений с ключами a,b,c,d,e,f и
значениями A,B,C,D,E,F


Режимы отправки сообщений в брокера

Синхронный - отправляем и ждем подтверждения об отправке, после чего отправляем следующее сообщение

Асинхронный - отправляем сообщение и не дожидаемся подтверждения, отправляя остальные сообщения. При получении
подтверждения выполняется переданный при отправке callback


Чтобы приложение Spring Boot запускалось на случайном незанятом порте, нужно указать пропертю server.port=0
Для кафки в каждой команде нужно указывать bootstrap-server для связи с кластером, это делается через
spring.kafka.producer.bootstrap-servers с передачей списка серверов. При этом для локального запуска через IDE нужно
будет поменять конфигурацию серверов, а конкретно - advertised.listeners для подключения внешних клиентов к кластеру
До этого клиентами были сами же сервера, так как скрипты я запускал через терминал на сервере с кафкой, а теперь
клиентом будет микросервис, запущенный на локалхосте, который не сможет связаться через внутреннюю сеть с кластером

Чтобы исправить эту ситуацию, нужно сделать несколько действий:
1. Вместо PLAINTEXT://kafka-serverX:9092 указать INTERNAL://kafka-serverX:9095. Таким образом мы обозначим внутреннего
слушателя, доступного в docker-сети. С помощью него сервера в кластере будут общаться друг между другом. Указать это
нужно как в KAFKA_LISTENERS, чтобы слушатель в принципе появился и слушал на указанном хосте и порте, так и в
KAFKA_ADVERTISED_LISTENERS, чтобы "прорекламировать" адрес этого слушателя всем клиентам

2. Добавить EXTERNAL://0.0.0.0:9092 в KAFKA_LISTENERS, чтобы создался слушатель EXTERNAL, принимающий соединения на всех
интерфейсах на порту 9092, а также добавить EXTERNAL://localhost:909X, где 909X - адрес, открываемый в контейнере
наружу, в KAFKA_ADVERTISED_LISTENERS, чтобы клиенты по этой строке могли подключиться к внешнему слушателю. Тогда при
запросе на localhost:909X докер пробросит этот запрос на порт 9092 и попадет в слушателя EXTERNAL.

3. Указать имя внутреннего слушателя в KAFKA_INTER_BROKER_LISTENER_NAME - INTERNAL, чтобы его могли использовать
остальные серверы кластера для репликации, запросов от контроллера и тд

4. Указать маппинг между именами слушателей и протоколами передачи данных в них в KAFKA_LISTENER_SECURITY_PROTOCOL_MAP.
В нашем случае нужно для всех слушателей будет поставить PLAINTEXT, так как данные передаются в сыром виде без SSL и
тд: ИМЯ_СЛУШАТЕЛЯ:PLAINTEXT,...

После этого в bootstrap-servers внутри контейнера нужно будет указывать 9095 порт вместо 9092, а для приложения нужно
будет указывать localhost:9092,localhost:9093,localhost:9094


Чтобы создать новый топик в Spring Boot приложении, можно создать бин типа NewTopic с помощью TopicBuilder, указав ему
имя - .name("<ИМЯ>"),
количество партиций - .partitions(<КОЛИЧЕСТВО>),
количество реплик на остальных серверах - .replicas(<КОЛИЧЕСТВО>),
свойство min.insync.replicas, отвечающее за минимальное количество серверов, которые должны быть синхронизированы с
лидером, чтобы продюсер мог еще что-то записать в брокера - .config("min.insync.replicas", <КОЛИЧЕСТВО>).
Если при запросе от продюсера лидер установит, что количество синхронизированных реплик меньше установленного
количества, то он откажется записывать новые данные. Если же количество будет больше либо равно установленному, то
лидер запишет данные у себя и реплицирует их на остальные сервера.

Пример полученного бина:
@Bean
public NewTopic exampleTopic() {
    return TopicBuilder.name("product-created-events-topic")
        .partitions(3)
        .replicas(3)
        .config("min.insync.replicas", "2")
        .build();
}


Чтобы записывать в топик в асинхронном формате, можно использовать автоматически настроенный бин KafkaTemplate,
параметризовав его классом ключа и классом значения
После внедрения бина можно использовать метод send(topicName, key, value), получив в результате CompletableFutute
На этом cf можно написать собственный callback через cf.whenComplete((result, exception) -> {...}), где exception будет
null для успешной отправки.

Также есть возможность использовать синхронную отправку сообщения, вызвав .get() на полученном cf. Тогда в результате
уже будет записан тот самый result, который можно было обработать в whenComplete

В этом result (SendResult<<KEY_TYPE>, <VALUE_TYPE>>) будут топик, партиция, оффсет сообщения в партиции и т. д.

Кафка распределяет сообщения по партициям на основании хэшкода ключа. Если ключ не указан, то round robin


Свойство spring.kafka.producer.acks устанавливает количество подтверждений для сообщения, чтобы оно считалось успешно
отправленным. Значение 0 означает, что сообщение всегда считается успешно отправленны, численное значение будет говорить
о количестве серверов кластера, в которых должно сохраниться и подтвердиться сообщение. Значение all будет ожидать
подтверждения от всех серверов, на которые производится репликация топика. По умолчанию стоит 1 - подтверждение только
от лидера.

В ответе могут приходить два типа ошибок - Retryable и NonRetryable. При получении ошибки первого типа продюсер
продолжит пытаться отправлять сообщение с таймаутом в 2 минуты по умолчанию. При получении ошибки второго типа
повторной отправки не будет.

С помощью свойства spring.kafka.producer.retries можно установить количество ретраев отправки сообщения при retryable
ошибке

С помощью свойства spring.kafka.producer.properties.retry.backoff.ms можно установить время между попытками ретрая (по
умолчанию 100 мс)

С помощью свойства spring.kafka.producer.properties.delivery.timeout.ms можно установить максимальное время на повторные
отправки сообщения (по умолчанию 2 минуты). По истечении вылетает TimeoutException

С помощью свойства spring.kafka.producer.properties.linger.ms можно установить время, в течение которого будут
накапливаться в буфере сообщения, после чего отсылаться одним батчем

С помощью свойства spring.kafka.producer.properties.request.timeout.ms можно установить время, в течение которого будет
ожидаться ответ с подтверждением от брокера

Нужно настраивать свойства так, чтобы выполнялось: delivery.timeout.ms >= linger.ms + request.timeout.ms
Это позволит в худшем случае совершить хотя бы одну попытку отправки сообщения

Для совершения всех попыток нужно брать delivery.timeout.ms с запасом

Можно провести эксперимент после установки acks=all: запустить весь кластер из трех серверов, отправить сообщения с 3,
2, 1 активным сервером. При 3 и 2 все должно быть в порядке, а при 1 посыпятся ошибки NOT_ENOUGH_REPLICAS и будут ретраи
После этого можно опять запустить остановленный контейнер и сообщение в итоге дойдет до брокера

Мы задали min.insync.replicas при создании топика. Позже это значение можно поменять через CLI следующим образом:
./kafka-configs.sh \
    --bootstrap-server kafka-server1:9095,kafka-server2:9095,kafka-server3:9095 \
    --alter \
    --entity-type topics \
    --entity-name product-created-events-topic \
    --add-config min.insync.replicas=1

После этого можно будет проверить все через ./kafka-topics.sh --describe

При изменении значения будет меняться количество ответов, которые ожидает получить продюсер при отправке сообщения при
установленном acks=all

Еще из интересного можно попробовать установить linger.ms и посмотреть, как сообщения будут отправляться батчем


Если в сервисе присутствует несколько топиков и для каждого из них ожидается свой тип ключей и значений, то понадобится
несколько kafkaTemplate, типизированных по-разному
Для этого можно создать в виде бина мапу, в которой будут все конфигурационные значения, которые хочется внести
При этом в качестве ключей мапы можно использовать ProducerConfig.SOME_CONFIG_PROPERTY, чтобы точно не ошибиться в
названии конфигурации, которую хочется засетить

Затем нужно создать ProducerFactory<<KEY_TYPE>, <VALUE_TYPE>>, передав в конструктор DefaultProducerFactory
конфигурационные значения

Затем можно уже создать индивидуальный KafkaTemplate, передав ему в конструктор созданную фабрику продюсеров


Идемпотентность продюсера
Может быть такое, что продюсер отправил сообщение, оно сохранилось в брокера, но при этом не отослалось подтверждение
Тогда продюсер еще раз попытается отправить сообщение, при этом оно опять сохранится в брокера
И если в этот раз подтверждение придет, то в брокере будет записано два одинаковых по смыслу сообщения
Это не страшно, если они обрабатываются идемпотентно. Например, если это gps-координаты
Но если это банковская операция, то сохранение двух сообщений вместо одного имеет значение

Чтобы продюсер в таких случаях сохранял только одну копию сообщения, можно воспользоваться свойством
spring.kafka.producer.properties.enable.idempotence

Свойство spring.kafka.producer.properties.enable.idempotence включает идемпотентный режим работы продюсера, при котором
брокер отслеживает sequence number сообщений, отправленных продюсером в рамках какой-то партиции. Если sequence number
ожидаемый, то сообщение записывается; если меньше ожидаемого, то сообщение не записывается, но отправляется успешный
статус записи; если номер больше ожидаемого, то выбрасывается исключение OutOfOrderSequenceException. По умолчанию это
свойство true

Это свойство может неявно стать false, если acks != all, retries <= 0 или max.in.flight.requests.per.connection > 5

Свойство spring.kafka.producer.properties.max.in.flight.requests.per.connection регулирует, сколько максимально
одновременно может быть запросов на отправку сообщения, которые ждут ответа


Получение сообщений из брокера в коде
@KafkaListener можно писать над методом или над классом. Позволяет прослушивать определенные топики, указанные через
topics = <ИМЯ_ТОПИКА>. Если написать над методом, то туда можно десериализовать какие-либо сущности из сообщения.
Если написать над классом, то методы можно помечать KafkaHandler. И работать будет тот метод, в котором первый аргумент
совпадает с классом десериализованного объекта

Для консюмера нужно указывать свойства в spring.kafka.consumer
Ему можно оставить такие же bootstrap-servers, но нужно заменить сериализаторы на десериализаторы, а также указать
group-id и spring.json.trusted.packages, чтобы сообщения могли корректно десериализоваться в доменные объекты.
Без указания spring.json.trusted.packages не будет доверия к десериализованным объектам, а значит они не будут
переданы в обработчик


После этого по аналогии с ProducerFactory нужно будет создать ConsumerFactory<String, Object> через передачу
конфигурационных свойств в DefaultKafkaConsumerFactory

Затем нужно будет создать ConcurrentKafkaListenerContainerFactory, создав экземпляр и вызвав на нем setConsumerFactory,
передав туда созданную фабрику консюмеров

Чтобы наш слушатель, аннотированный @KafkaListener, использовал в своей конфигурации именно нашу фабрику контейнеров,
нужно указать в параметре containerFactory название бина с созданной фабрикой контейнеров


В случае, когда в топик попадает сообщение, которое не получится десериализовать с помощью JacksonJsonDeserializer,
например, когда добавляется еще один продюсер, который отправляет уже не JSON, а просто строки, сервис будет вечно
пытаться десериализовать это сообщение, но при этом будет вылетать ошибка DeserializationException
Таким образом, сервис просто напросто станет полностью недоступен

Чтобы избежать подобной ситуации, нужно добавить обертку над JacksonJsonDeserializer -- ErrorHandlingDeserializer, а вот
уже ему указать ErrorHandlingDeserializer.VALUE_DESERIALIZER_CLASS в виде JacksonJsonDeserializer.class
Тогда если сообщение не десериализуется, ошибка об этом просто будет выведена в консоль, но само сообщение будет
пропущено


При полученной конфигурации необработанные сообщения просто пропускаются. Возможно, это не лучший вариант, потому что
там все же есть какие-то данные, на которые хотелось бы посмотреть
Для этого существует механизм отправки необработанных сообщений в DLT - Dead Letter Topic
По сути это новый топик, который имеет такое же название, как у топика, из которого происходит потребление сообщений, но
с префиксом .DLT

Пересылку необработанных сообщений нужно устанавливать в фабрике контейнеров с помощью setCommonErrorHandler,
устанавливая DefaultErrorHandler поверх DeadLetterPublishingRecoverer, которому нужно передать kafkaTemplate

KafkaTemplate нужно создать отдельный по аналогии с тем, как создавался шаблон в продюсере
Но этот шаблон уже должен ключ сериализовать в String, а значение в byte[]


Сейчас все сообщения отправляются в DLT при ошибке десериализации
Нужно также отправлять их туда при ошибке при исполнении бизнес-логики внутри обработчика в консюмере
Также можно заметить, что используется подход с явным созданием обработчика ошибок для
ConcurrentKafkaListenerContainerFactory

От этого всего можно уйти, подключив аннотацию @EnableKafkaRetryTopic на конфигурационный класс
Эта аннотация позволяет использовать декларативный подход для работы с исключениями при исполнении бизнес-логики в
обработчике, а также для работы с DLT

Исключения при исполнении бизнес-логики можно поделить на те, после которых обработку можно повторить (Retryable.
Например, timeout при запросе в сторонний сервис), а также те, после которых обработку повторять не имеет смысла
(NonRetryable: NPE, непредвиденные ошибки, ошибки валидации)

Также хорошо бы иметь возможность ограничить количество попыток для повторной обработки сообщения и интервал между
попытками

Все это позволяет сделать аннотация @RetryableTopic(attempts = "<общее количество попыток>", backOff = @BackOff(delay =
<базовая задержка>, multiplier = <множитель задержки на каждую следующую попытку>), include = {
<повторяемое исключение>.class, ...} ИСКЛЮЧАЮЩЕЕ ИЛИ exclude = {<неповторяемое исключение>.class, ...})

Эта аннотация может ставиться как на конкретный метод-обработчик, так и на класс с разными методами обработчиками. Она
работает следующим образом: создается прокси-метод, который отлавливает исключения, и если класс исключения можно
привести к одному из классов из include ИСКЛЮЧАЮЩЕЕ ИЛИ если класс исключения нельзя привести ни к одному из классов
из exclude, то обработка повторяется. Суммарное количество попыток в таком случае, - не повторов, а именно попыток, -
составляет указанное <общее количество попыток>, по истечении которых сообщение отправляется в DLT. Каждая следующая
попытка производится с задержкой delay * multiplier^i, где i - номер попытки от 0 до <общее количество попыток> - 1
включительно. Если же исключение не нужно повторять, то оно сразу отправляется в DLT.

Для обработки сообщений из DLT существует аннотация @DltHandler, которая позволяет получать сообщения и обрабатывать их
каким-то образом
