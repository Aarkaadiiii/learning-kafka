Стандартное правило именования событий (Event) в Kafka -- СущностьДействиеEvent. Например: PaymentCreatedEvent

При этом Event - часть Message. Event сериализуется и является составной частью (телом, скорее всего) Message.
Message же при этом содержит Key - ключ, по которому производится распределение по партициям (если указан); Timestamp -
время создания сообщения; Headers - заголовки в формате ключ-значение для хранения дополнительной информации.

Топик делится на партиции, в которых сообщения упорядочены. Упорядочены они по времени добавления, и считываются
только в таком порядке. При этом для каждого потребителя хранится для каждой партиции оффсет -- смещение относительно
начала партиции, которое определяет следующее считываемое сообщение. При этом нельзя вставлять данные в середину или
начало партиции - только в конец, чтобы сохранялась упорядоченность. Хранимые данные еще и неизменяемы. Их нельзя
удалить и изменить вручную. Удалятся они только после того, как пройдет заданное количество времени. По умолчанию
это количество времени составляет семь дней.

Партиции - единицы параллелизации топика. Из них чтение идет параллельно, поэтому нельзя полагаться на порядок отправки
сообщений, если они записаны в разные топики. Чтобы сообщения обработались в определенном порядке, нужно указать
сообщению ключ. При указании одного и того же ключа сообщения будут попадать в один и тот же топик.

Кафка поддерживает репликацию. Можно создать кафка-кластер, где один сервер будет выступать в качестве лидера, а
остальные - в качестве фолловеров. Лидер будет производить запись сообщений, а фолловеры будут реплицировать у себя
записанные в лидера данные. При отказе лидера, им становится один из фолловеров. То есть лидер принимает данные от
продюсеров, отправляет данные консюмерам, а также отправляет данные на фолловеров для репликации.
Если бы такая схема работала на всю структуру и лидер для каждого топика и каждой партиции был бы один, он бы стал узким
горлышком, а остальные сервера в кластере бы простаивали. Чтобы избежать этого, используется механизм распределения
лидеров для каждой партиции каждого из топиков. Таким образом каждый из серверов кластера становится лидером для какого-
то подмножества партиций, и нагрузка распределяется между всеми (поровну, видимо).
Как уже и было сказано, при отказе лидера какой-то партиции, лидером автоматически назначается какой-то из фолловеров.



Первый запуск кафки.
После установки кафки находим папку со скриптами (bin) и переходим в нее
Затем выполняем команду для рандомного uuid: ./kafka-storage.sh random-uuid (или виндовс аналог)
Новые версии kafka работают только с kraft, zookeeper убрали, поэтому форматировать ничего не нужно
Для запуска в виде docker контейнера можно указывать свойства из .properties файла в виде переменных окружения, заменяя
"." на "_" и добавляя префикс "KAFKA_"
Сгенерированный id будем использовать как id кластера - переменную окружения CLUSTER_ID
После этого запускаем контейнер с этой переменной окружения и видим, что все
У нас запустится кластер с одним сервером

Для запуска нескольких серверов в кластере для каждого из них нужно немного поменять конфигурацию запуска, опять же
используя переменные окружения
Нужно установить следующие переменные окружения:
KAFKA_NODE_ID - id сервера в кластере в формате одного числа. Числа должны быть разными для разных серверов (1, 2, ...)

KAFKA_LISTENERS - хост и порт для контроллера и брокера в формате
PLAINTEXT://{имя_сервера_в_сети_docker}:9092,CONTROLLER://{имя_сервера_в_сети_docker}:9093. На этих адресах сервер будет
слушать внутри контейнера

KAFKA_CONTROLLER_QUORUM_VOTERS - контроллеры, которые в рамках кластера управляют распределением лидеров, фолловеров. В
формате {id_сервера_в_кластере}@{адрес_контроллера_с_хостом_и_портом} для всех серверов через запятую

KAFKA_ADVERTISED_LISTENERS - строка подключения к брокеру для внешних клиентов в формате
PLAINTEXT://{адрес_сервера}, где адрес можно выбрать либо внутренний, для доступа из Docker-сети, либо localhost:порт
для доступа с хостовой машины.

KAFKA_LOG_DIRS - директория с логами, метаданными и снапшотами. Всем можно указать /var/lib/kafka/data и создать
отдельный volume

KAFKA_PROCESS_ROLES - роли сервера в кластере (контроллер, брокер, или обе)

KAFKA_CONTROLLER_LISTENER_NAMES - имя слушателя, который является контроллером, из проперти KAFKA_LISTENERS
Мы указали двух слушаетелей: CONTROLLER и PLAINTEXT. И именно CONTROLLER должен быть контроллером, поэтому его имя и
нужно указать.




Kafka topic CLI

Создание топика:
./kafka-topics.sh \
    --create \ // создать топик
    --topic payment-created-events-topic \ # имя топика
    --partitions 3 \ # количество партиций. должно быть не меньше предполагаемого количества подключений
    --replication-factor 3 \ # количество копий каждой партиции. не может быть больше количества запущенных серверов
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092 # список брокеров в кластере. если
        какой-то недоступен, то обращение идет к другому

Просмотр списка топиков (только имена):
./kafka-topics.sh \
    --list \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092

Просмотр данных о топиках:
./kafka-topics.sh \
    --describe \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092

Удаление топика:
./kafka-topics.sh \
    --delete \
    --topic payment-created-events-topic \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092


Kafka producer CLI

Отправка сообщения. Сначала выполняем команду, а потом вводим сообщение в консоль:
./kafka-console-producer.sh \
    --topic payment-cancelled-events-topic \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092
При отсутствии нужного топика он создастся и сообщение дойдет до него (при проперти auto.create.topics.enable=true).
Автосоздание топика не лучшая практика, потому что мы не задаем ему конфигурацию.

Для отправки сообщения в определенную партицию нужно указать ключ. Для этого можно использовать следующую команду:
./kafka-console-producer.sh \
    --topic payment-cancelled-events-topic \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092 \
    --reader-property="parse.key=true" \ # парсить ключ в сообщении
    --reader-property="key.separator=:" # ключ до двоеточия, контент - после


Kafka consumer CLI

Команда для считывания всех сообщений топика с самого начала каждой партиции
./kafka-console-consumer.sh \
    --topic payment-cancelled-events-topic \
    --bootstrap-server kafka-server1:9092,kafka-server2:9092,kafka-server3:9092 \
    --from-beginning

Чтобы выводились ключи, нужно добавить --formatter-property print.key=true
Чтобы выводились ТОЛЬКО ключи, нужно добавить --formatter-property print.value=false
Чтобы выводились только НОВЫЕ сообщения, нужно убрать --from-beginning
Чтобы вывести сообщения из определенной партиции, нужно добавить --partiton <НОМЕР>

Если запустить несколько consumer-ов, им всем будут приходить новые сообщения

Можно проверить, что партиции обрабатываются в асинхронном формате, и при этом сообщения с одним и тем же ключом
попадают в одну и ту же партицию. Проверять будем на топике с несколькими партициями - payment-sent-events-topic
Для этого запишем 6 сообщений с ключом key и значениями A,B,C,D,E,F, а также 6 сообщений с ключами a,b,c,d,e,f и
значениями A,B,C,D,E,F
